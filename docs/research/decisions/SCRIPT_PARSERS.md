# スクリプト構文解析器の比較と段階導入（P5-03）

日付：2026-11-05。対象：`src/script.rs` の静的スクリプト判定。前提：検査対象を**実行しない**、入力・時間・メモリに上限、MSRV 1.85 の既定ビルドを壊さない、GPL/AGPL を持ち込まない。

## 候補

| 言語 | 候補 | 長所 | 短所・リスク | 判断 |
|---|---|---|---|---|
| PowerShell | Microsoft公式パーサー（`System.Management.Automation.Language.Parser::ParseFile`）を別プロセスで呼ぶ | 正確なAST。実行はしない | ファイルごとにPowerShell起動（数百ms）、Windows専用、子プロセスの資源管理が必要 | 将来の任意機能候補。既定では採用しない |
| PowerShell | Rustで字句解析（文字列・ヒア文字列・コメント・`$()`） | 依存なし、決定的、Linux/CIでも同じ結果、上限管理が容易 | 完全なASTではない（スクリプトブロック・パイプラインの意味までは見ない） | **第1段階として採用（本PR）** |
| JavaScript | `oxc_parser` / `swc_ecma_parser`（MIT） | 正確なAST、高速 | 依存が大きい、MSRVが1.85を超える版が多い | 第2段階で別featureとして比較 |
| Python | `rustpython-parser`（MIT） | 正確なAST | 依存が大きい、更新頻度 | 第3段階で比較 |
| 共通 | tree-sitter（MIT、C実装） | 多言語、エラー耐性 | Cコードのビルド・ファジングが必要、文法ごとのライセンス確認 | 保留 |

## 第1段階（本PR）で解決したこと

- `.psd1` マニフェストのエクスポート一覧など、**文字列として列挙されたコマンド名**を呼び出しと誤認していた問題（実機で残っていた誤警告の主因）。
- 文字列が実行に渡る場合（`iex "..."`、`Invoke-Expression '...'`、`"$( ... )"`）はコードとして読み、検出を弱めない。
- データ（URL、資格情報ストア名、Runキー、AMSIの型名）は文字列内でも根拠として残す。

## 未解決（次の段階）

- JavaScript/Python のテンプレート文字列・f文字列内のコード、関数定義だけで呼ばれない処理（未到達コード）の区別。
- PowerShellのスクリプトブロック変数・`&`/`.` 呼び出しの追跡、`-EncodedCommand` 以外の動的生成。
- 動的生成・ネット経由のコードの復元は原理的に完全にはできない。上限到達は `incomplete` とする（既存）。
